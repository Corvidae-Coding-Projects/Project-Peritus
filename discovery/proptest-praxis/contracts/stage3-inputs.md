## Boundary and caller evidence

The campaign calls the real public `control::InputLedger::{apply,capture,incorporated_conversation,capture_with_replies}`, checked `InputSelection`/`ControlText` constructors, and public `InputCapture::with_file_context`. It compares every immutable revision field, pending order, generation, exact incorporation/request/manifest binding, captured instruction bytes, and eligible reply identity. Ordinary serde serialization/deserialization reconstructs the actual ledger type; this is **aggregate reconstruction**, not a claim of filesystem or daemon crash/restart qualification.

Read `control.rs`, `control/{inputs,text,identity/input,identity/invocation}.rs`, all of `control/inputs/{transition,capture}.rs`, and the control/input navigation maps. The pure reducer creates a successor proposal; acceptance becomes durable only when the daemon's C0 owner commits it.

Actual callers inspected:

- `peritus-daemon/src/product_run/workbench/inputs.rs` authenticates owner/workspace and maps user queue intentions. Host-only incorporation has no A3 user-intent variant.
- `product_run/interaction/inputs.rs` projects accepted immutable revisions as public received input, independently of inference admission.
- `product_run/interaction/live/request.rs` checks current generation and network/persistence state, calls durable preparation, reserves the role's request, and only then publishes incorporated activity.
- `product_control/inputs.rs::prepare_execution_with_observations` rejects stale capture generation before constructing request admission; `prepare_inputs_with_observations` binds captured exact revisions, semantic request digest and independent source manifest through a C0 operation. Operation-level retry idempotence belongs to that store.
- `product_run/interaction/live.rs::{tool_control,admit_tool}` compares the live ledger generation with the request's input revision and yields on drift. This campaign does not execute those daemon dispatch paths.

The distinction matters: a row can be accepted and queued, then appear in a read-only candidate capture, then be incorporated into a durable request. Pure `InputLedger::apply(Incorporate)` accepts exact items and contains no generation argument; it must not be assigned the stronger daemon generation-fencing contract. Reusing an enqueue or invocation identity rejects at this API even when content matches. This is separate from exact C0 operation receipt replay.

## Independent model

An ordinary list retains immutable input content, author, dependencies, corrections and all content revisions, with a separate pending list and immutable invocation list. Future operands and saved captures come from this reference state, never production lookups. Validity is expressed through identity uniqueness, append-only content revisions, pending dependency order, and earlier incorporated prerequisites. Captures derive eligible dependency-complete queued items, excluding held items and their blocked descendants, then independently render exact `User: ` and public-reply text.

No production transition, capture, validator, verified predicate, serialized state, or `InputRevision` getter supplies an expected outcome. Production getters are only compared to case/model expectations. Checked ID constructors translate known logical identities. Unicode/terminal-control validation and byte ceilings are explicit input-level checks. Public reply capacity preflight includes the explicit 32-byte per-reply reserve at this API boundary; formatter and reserve behavior are correspondence targets, not tokenizer or provider-cost claims.

## Histories and invariants

Generated cases begin with one to six short source-defined inputs with arbitrary acyclic prerequisite masks and held roots, followed by up to `min(max_steps,128)` operations over a small ID domain. They enqueue, edit, hold/unhold, withdraw, move/reorder, correct incorporated history, capture/save old selections, incorporate current/explicit/saved selections, replace caller-provided reply maps, import corrupt aggregates, append bounded file context, and serialize/reconstruct. Revisions can select latest, first, prior, future or zero; errors must retain complete accepted state and are followed by real captures and further transitions.

The suite checks immutable content/author history; supersession rather than in-place edit; exact pending order; dependency blocking and release; stale and missing identities; independent correction identities; accepted versus candidate versus incorporated representations; immutable request/manifest digests; empty invocations; duplicate-ID rejection; final reply suppression until a later input; and input generation changes for governing changes but not self-incorporation. Fixed witnesses cover empty state and actual input text byte limits at 8191/8192/8193 in ASCII and multibyte Unicode. File-context operations independently verify exact concatenated bytes and every capture metadata field for suffixes bounded to 16 KiB, with fixed empty, one-byte, multibyte UTF-8, and exact 16 KiB ASCII/UTF-8 witnesses. Generated file-context operations use the same explicit local allocation bound.

`MAX_REQUEST_CONTEXT_BYTES` is not a small request quota: `control.rs` forwards `ProtocolLimits::PRODUCTION.max_text_bytes()`, and `peritus-model-protocol/src/bounds.rs` defines `PRODUCTION == ARCHIVE`, whose fields are `u32::MAX`. The aggregate ceiling is therefore 4,294,967,295 bytes on this target. The initial `FileContextBoundary` fixture attempted that allocation and the owner process was killed with recorded maximum RSS 6,671,364 KiB, approximately 6.36 GiB (`runs/stage3-inputs-examples-first/inputs/process.json`, exit -9). The case and process evidence remain retained. The existing serialized `FileContextBoundary(i8)` variant is preserved without reinterpretation: replay returns `setup-incomplete: actual aggregate representation ceiling exceeds bounded local campaign` before allocating. The Stage 3 controller must classify that prefix as incomplete setup, never a product failure or successful skipped case. New fixed/generated campaigns do not emit that variant. The product bound is unchanged; exact aggregate ceiling minus one/exact/plus one remains unqualified here.

Saved captures deliberately may become stale. This pure-API campaign tests exact immutable selection validity, not implicit generation admission. Serde accepts some structurally typed but semantically invalid aggregates; the real capture/reducer must reject them at use. Corruption families cover zero governing generation on a nonempty ledger, zero revision, zero author and duplicated pending order. The current live ledger is never replaced by these invalid imports.

Metrics count accepted enqueue/edit/hold/unhold/withdraw/move/reorder/correction/incorporation operations; rejected typed transitions; exact captures and pending/reply contributions; saved snapshots; request attempts including empty bindings; reply map changes; reconstructed aggregates; each invalid import family; bounded file-context append/byte totals, empty and multibyte contributions, and the maximum tested suffix size. These counters make no aggregate-capacity acceptance/rejection claim. A `continued_after_rejection` count is followed by verified complete state and captures in the same check. Root must gate observed mechanisms rather than equating generated case count with completeness.

## Calibration

`calibration/stage3-inputs.patch` intentionally misclassifies incorporation as a governing generation change in the real reducer by excluding `Reorder`, rather than `Incorporate`, from generation advancement. `calibration_case()` enqueues one exact input, incorporates it, and reconstructs. The model requires generation to remain unchanged during incorporation, so the mutation must produce a behavioral failure. This canary represents the actual failure mechanism where admitting a request invalidates its own subsequent effect fence. No deliberate mutation has been applied by this worker.

## Explicit gaps

This campaign covers the pure input domain and serde boundary. It does not qualify C0 persistence, authenticated authority, provider invocation, model/effort updates, generation drift between daemon dispatch boundaries, cancellation/finalization races, process crash recovery, typed IPC, client presentation, attachment/brief/compacted-reply selection, arbitrary imported history corruption, unbounded revision overflow, exact aggregate request/file-context capacity edges, or the full Stage 3 exit. Those remain separate daemon and settlement campaigns or require a deliberately provisioned capacity environment. No passing result or product bug is asserted before final execution evidence.
