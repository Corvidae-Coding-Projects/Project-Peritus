## Confirmed defect RSI-F0-01: valid evaluation schedule disables daemon mutations

The consumer creates a fresh E3 campaign with finalized real input artifacts, builds and records a complete checked plan, then commits `RequestSchedule`. It does **not** fabricate a D3 acknowledgement, task verdict, publication, or activation. The journal contains one pending `peritus.eval.schedule-rollout.v1` outbox row.

Starting an actual `peritusd serve` with that journal, then invoking the actual CLI status command yields:

```json
{"diagnostic":"PERITUS-DAEMON-PLATFORM-001 while delivering durable outbox destination peritus.eval.schedule-rollout.v1","mutation_ready":false,"readiness":"ready-read-only"}
```

The outbox remains claimed (state 2, attempts 1, fence 1). Restarting the same owned daemon reproduces the failure with attempts 2/fence 2. `shutdown --wait` reports `daemon reported unclean shutdown completion` (CLI exit 14); the owned daemon exits 1. A fresh independent replay reproduces all of this with a different database and process.

Cause: `startup/runtime/runner.rs` installs only `DestinationRouter::production_children`. E3/F0 destination handlers exist in `outbox/handlers.rs`, but the full router requires a `DurableOutboxPort` for which no implementation exists. `outbox/router.rs` rejects missing handlers; `outbox/pump.rs` treats that operator-recovery error as a daemon-wide read-only condition and terminates its worker. This is missing production execution wiring, not a failed candidate or evaluator.

Raw evidence: the project-local launcher/replay was independently operated and reproduced the same failure under `preserved-replay/` (consumer build 5.82 seconds). The equivalent earlier evidence is `replayed-unhandled/status.json`, `outbox.json`, `shutdown.json`, `daemon-exit.json`, `results.json`, `schedule-request.txt`, `executables.json`, and `peritus.sqlite3`. The first reproduction plus restart is retained under `runtime-unhandled/`; its initial consumer's final readback failed because the driver shadowed its expected-state variable, not because Peritus replay was incorrect. That driver defect was corrected before the final seeded comparison and fresh replay.

## Smallest honest production completion boundary

A generic acknowledgement or registering no-op handlers is invalid. E3 effect transitions require exact claimed directives and real scheduler/runtime observations.

1. Add durable resolution for complete frozen profiles, rollout specifications, executable/materialization roots, and ledgers. Execution directives contain only identities and request digests; the daemon presently cannot resolve them into runnable work.
2. Add authority-owner APIs for exact claimed schedule/start/terminal/publication settlement. Current domain frame dispatch uses ordinary commits, which correctly reject effect transitions without the native claim.
3. Implement the real D3 scheduler and C2/C3 candidate/evaluator execution adapter with bounded ownership, cancellation, finalized outputs, and a sealed evaluator boundary.
4. Drive complete-ledger analysis, artifact report staging, exact evidence admission, and publication settlement, including restart recovery.
5. Compose actual E1 materialization, D2 review, F0 attribution/selection, and B0/B1 approve-once activation/rollback; expose a supported operator workflow.

Preventing a single unsupported campaign from disabling unrelated daemon work is a useful narrower repair. It cannot be reported as completing the statistical RSI/F0 candidate system.
