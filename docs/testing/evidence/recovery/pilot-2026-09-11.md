# Recovery pilot evidence — 2026-09-11

## Scope

- Source: `f75f5dee3976b1c72b85e78fa1d6c50475d5d8fa`
- Branch: `test/proactive-recovery`
- Host: Linux x86_64, kernel `6.17.1-300.fc43.x86_64`
- Toolchain: `rustc 1.97.1`, `cargo 1.97.1`
- Build concurrency: `CARGO_BUILD_JOBS=2`
- External network/provider calls: none; all provider behavior was local and scripted

## Confirmed defect 1: explicit cancellation became restartable

Boundary: `ProductRunService::cancel` racing `ProductRunService::shutdown` after the scripted provider recorded exactly one request.

Deterministic fixture identities were run ID `e4` repeated 16 bytes, workspace ID `e5` repeated 16 bytes, and provider IDs `e1`, `e2`, and `e3` repeated 16 bytes. The test waited for the provider request observation with cooperative task yields under a five-second watchdog, then cancelled and shut down immediately.

Independent oracle: reload the persisted product record from the service's durable directory and count recorded provider requests. Before the fix, all three fresh fixture runs produced `RecoveryRequired` instead of `Cancelled`; each recorded exactly one provider request. The focused command exited 101 on every reproduction:

```text
timeout 20s env CARGO_BUILD_JOBS=2 cargo test -q -p peritus-daemon explicit_cancel_racing_shutdown_remains_cancelled_in_durable_state -- --nocapture
left: RecoveryRequired
right: Cancelled
```

Cause: shutdown used the same cancellation channel as explicit user cancellation, then classified every run that had been nonterminal at shutdown inventory as restartable unless it completed. It did not retain which cancellation was explicitly requested by the user.

Repair: retain the user-cancellation intent in the live run record. Shutdown preserves or finishes that run as `Cancelled`; shutdown-originated cancellation remains `RecoveryRequired`. Retry and terminal follow-up reset the live intent.

After-fix verification:

```text
timeout 90s env CARGO_BUILD_JOBS=2 cargo test -p peritus-daemon product_run::tests::recovery -- --nocapture
3 passed; 0 failed
```

## Confirmed defect 2: valid receipts appended after a crash tail were lost

Boundary: effect receipt append/reload around an incomplete final frame. The fixture wrote and completed effect ordinal 1, appended a durable partial frame (`length = 64`, payload `{`), restarted, replayed ordinal 1, completed ordinal 2, and restarted again.

Independent oracle: the ledger byte length returns exactly to its pre-crash clean length before ordinal 2 is admitted, then both ordinals replay after the second restart. A complete malformed frame is a negative control: it remains byte-for-byte present and fails closed.

Before the fix, all three fresh fixture runs exited 101 during the second restart because the old partial frame consumed bytes from the later valid frame:

```text
timeout 20s env CARGO_BUILD_JOBS=2 cargo test -q -p peritus-product-runner append_after_truncated_tail_remains_replayable_after_another_restart -- --nocapture
replay first after restart: Tool("decode effect receipt: key must be a string at line 1 column 2")
```

Cause: load ignored an incomplete final frame but did not remove it. Subsequent append-only records were written after the invalid suffix and became undecodable on the next process restart.

Repair: after validating every complete prefix frame, truncate and `sync_data` only an incomplete suffix before accepting more effects. Complete malformed frames still fail closed without truncation.

After-fix verification:

```text
timeout 90s env CARGO_BUILD_JOBS=2 cargo test -p peritus-product-runner developer_tools::receipt -- --nocapture
4 passed; 0 failed

timeout 180s env CARGO_BUILD_JOBS=2 cargo test -p peritus-product-runner
285 passed; 0 failed; 1 ignored

timeout 180s env CARGO_BUILD_JOBS=2 cargo test -p peritus-daemon
211 passed; 0 failed; 2 ignored
```

## Containment and remaining matrix

All cases used disposable temporary repositories and state directories. No native service, live provider, credential, or unrelated process was touched. The post-run process census found no process rooted in this worktree or a `resume-fixture` repository. Test watchdogs were 20–180 seconds and build fan-out stayed at two jobs.

This pilot did not yet exercise actual process termination between every receipt write/effect/completion boundary, persistence I/O failures, command control races, repeated startup admission failures, or terminal follow-up versus finalization. Those remain expansion cases; these results do not claim power-loss durability.
