## Source-reviewed behavior

### Resource and reservation invariants

"src/resource/capacity.rs" connects executable quantity and fits_within to exact sequence specifications. "src/verified/reservations.rs:79-202" defines uniqueness of reservation dispatch/work identities, worker and work identity uniqueness, exact reservation-to-worker ownership, exact reservation-to-work owner/revision/request/attempt binding, active-reservation limit, global resource bounds, worker concurrency, and worker-local resource bounds.

"src/selection/capacity.rs" uses u128 for live sums. Given the production active-reservation maximum of 4,096 and u64 resource quantities, the implementation and proof bound intermediate values without overflow. Insertion/removal and stable work/worker mutations preserve the mathematical invariant. "src/verified/reservations/readiness.rs:10-54" additionally binds live reservations to Reserved, Running, or Cancelling work and to retained dispatch history.

### Selection

"src/selection/model.rs:50-133" defines an admitted work/worker pair from actual state: queued work, available worker, full owner identity equality, supported work class, global capacity, worker concurrency, and worker-local capacity. The internal selector in "src/selection.rs:186-357" proves that a returned pair satisfies this relation when the input state satisfies the reservation invariant.

Runtime ordering remains aged work first, then priority descending, enqueue ordinal ascending, and WorkId lexical order, with the first feasible worker in sorted worker order. The unchanged fairness test checks this ordering against a reference implementation. This checkpoint does not formally prove selected-minimum ordering, first-worker selection, None iff no admitted pair, or bounded fairness. The public select_next contract exposes only the weaker selection_is_feasible, which does not itself include queued phase, available worker state, or supported class.

### Dispatch and reservation mutation

"src/reducer/apply/dispatch.rs:10-134" defines exact input-based dispatch admission: reducer readiness, the selected pair relation, unused dispatch identity, active bound, dispatch ordinal, and next attempt. "src/state/mutation/reserve.rs:12-136" and its preparation/proof modules establish that a successful selected reservation binds work, dispatch, worker, owner, candidate revision, resource request, incremented attempt, used-dispatch retention, and dispatch-ordinal advancement while preserving readiness.

The production rejection order remains phase, active limit, duplicate dispatch, history limit, no feasible pair, attempt overflow, attempt bound, ordinal overflow, then admission disappeared. Source inspection found this consistent with the reachable pre-change ordering and error kinds. Ordinary tests cover active limit, duplicate dispatch, history limit, no feasible pair, and rollback. The public reserve_next contract proves conditional invariant preservation only; it does not prove exact Result, rejection payload, or complete success output semantics.

Reservation history insertion uses an executable ordered slot. The local mirror "/tmp/peritus-sol-scheduler244-reservation-slot-check.py" matched Python bisect_left in 110,240 exhaustive/random cases. This is finite test evidence, not a theorem. The proof states exact insertion at an existential valid position but does not prove canonical ordering or uniqueness of the resulting history.

The reservation constructor specification covers work, dispatch, worker, owner, attempt, revision, and resources. It omits dispatch token and started == false, although the production body sets both. Clone equivalence includes token and started state.

### Clone transport

Exact semantic Clone contracts exist for ResourceVector, WorkSpec, WorkRecord, WorkerDescriptor, WorkerRecord, SchedulerReservation, and SchedulerTerminal. Reservation cloning includes dispatch token and started state.

SchedulerBinding::clone formally covers limits and capacity only; it does not specify run ID, scheduler ID, or candidate revision. SchedulerState::reservation_clone_equivalent covers binding limits/capacity, workers, work, reservations, and used dispatches, but omits binding identities/revision, scheduler phase, sequence, event, digest, dispatch/enqueue ordinals, used commands, and terminal. Bodies copy those fields and ordinary replay/equality tests exercise them, but the formal contract only transports what the reservation reducer proof currently needs.

### Acknowledge and release transitions

The actual acknowledge and release wrappers were inspected through "src/state/mutation/reservation_update.rs", "src/state/mutation/work_update.rs:290-363", and "src/reducer/apply.rs:185-311". Tests demonstrate capacity release, unrelated reservation retention, replacement dispatch, late old-dispatch rejection, and replay.

The checkpoint does not formally establish exact lookup success/failure, exact target state frame, started == true plus Running after acknowledgement, exact removed reservation identity, exact retry/terminal/cause/phase values, or exact Result and error payload for those transitions. "src/work/phase.rs:18-53" is intentionally a minimal relation: Reserved, Running, and Cancelling retain reservations. It does not characterize started state or all lifecycle phases.

### Public boundary and escape review

The actual unchanged reducer, decoder, wire, durability, session, runtime, and daemon callers were inspected. Production command processing still goes through start/decide, durable session commit, and dispatch acknowledgement/failure/retry paths. select_next_for_dispatch is the internal production selector; repository uses of public select_next found by inspection are tests.

Unchanged wire-state validation rejects noncanonical or duplicate collections and checks resource vectors, reservation ownership/capacity, started versus Reserved/Running, ordinals, and digest. This is runtime evidence for admitted serialized state, not a formal decoder theorem.

No changed source contains assume, admit, axiom, external_body, trusted escape, verifier assumption, unsafe code, or newly added public executable precondition. Mutation modules remain crate-private. The WorkTerminal lint annotation is the narrow cfg_attr(verus_keep_ghost, allow(missing_docs, reason = ...)) needed for generated ghost projections. The direct SchedulerError negative proof control fails because SchedulerError, error::reject, and ErrorKind are ignored outside the current Verus boundary. This accurately limits the checkpoint; it does not establish that a future supported wrapper is impossible.

## Material performance risk

The prior implementation aggregated live reservations into ResourceVector values with merge-style checked_add, then used binary lookup. Checkpoint 244's "src/resource/capacity.rs:53-143" performs a linear scan for every quantity lookup. "src/selection/capacity.rs:49-326" performs one such lookup per reservation per requested resource kind for global and worker checks.

A valid dense shape has R active reservations, each with D ascending unique resource kinds, one queued request with Q=D kinds, and a capacity vector over the same D kinds. The checkpoint's selection capacity path performs work proportional to Q times R times repeated linear scans through D entries, and selection can repeat that work across queued work and workers. The independent static named-kind comparison model, "/tmp/peritus-sol-scheduler244-capacity-cost-model-v2.py", reports:
- R=64, D=Q=8: 981 baseline vs 2,340 checkpoint comparisons, 2.39x
- R=256, D=Q=64: 32,840 vs 534,560, 16.28x
- R=4,096, D=Q=256: 2,094,858 vs 134,774,912, 64.34x

This is a source-level operation-count model, not a wall-clock benchmark or asymptotic theorem. A separate worker is running fresh-target A/B/C measurements and implementing any substantiated correction. A suitable correction is verified ordered binary lookup or precomputed per-kind totals while preserving the exact predicates and rejection order.

6. Work/worker mutators found iff, exact phase/cause/terminal values, and complete frames.
7. Release helpers' exact matching reservation/work binding, result iff, exact removed record, and terminal/retry/phase correspondence.
8. Actual apply/decide/replay composition, exact errors and rollback, event/sequence/digest output, and proof that worker/work insertion establishes reducer readiness.
9. Full semantic Clone contracts for every SchedulerBinding and SchedulerState field and transport through decide/wire paths.
10. Complete WorkPhase/start invariant, including Reserved iff not started, Running iff started, Cancelling semantics, and exclusion of live reservations from all other phases.
11. Constructor/getter and exact lookup contracts for scheduler limits/binding, workers, work, reservations, and their identity/canonicality assumptions.
12. All-command state/event frames, replay composition, OBL-0150/effect termination, and formal fairness.
13. Resolution and measured validation of the dense-resource performance risk above.
