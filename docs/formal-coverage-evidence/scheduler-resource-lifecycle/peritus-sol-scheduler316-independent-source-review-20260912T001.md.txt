`src/state/mutation/worker_update.rs`; `src/state/mutation.rs` is not expected to change. That
two-path correction requires a focused follow-up source review, rather than a restart of this

## Source findings

### Actual command and Clone correspondence

`SchedulerCommandKind` remains the actual public command payload and is re-exported from the same
public surface after its declaration moved to the private `command/kind.rs` module. Its manual
semantic `Clone` exhaustively handles every variant and every payload field. Identity and digest
fields are copied exactly; `SchedulerBinding`, `WorkerDescriptor`, and `WorkSpec` use their actual
semantic clones. No command variant is omitted or collapsed.

The added semantic clones for `SchedulerBinding`, `SchedulerState`, `WorkerRecord`, and
`WorkRecord` cover all authoritative production fields needed to transport the cloned successor
through `decide`: immutable binding identities/revision/limits/capacity, scheduler phase,
sequence/event/digest, workers, work, reservations, used dispatches, enqueue/dispatch ordinals,
used commands, and terminal state. Nested worker/work/reservation terminal and payload relations
retain their exact identities and material values.

### Reservation lifecycle and reducer routing

Genesis establishes the strengthened reservation-reducer readiness relation. The relation now
connects live reservations in both directions with active work, enforces the expected
started-versus-phase relation, and retains every live dispatch identity in history. The actual
acknowledge-start transition and all five release families preserve this relation under their
documented pre-state conditions.

The production `reducer/apply.rs` match remains exhaustive. Pause, Resume, Drain, RetryWork,
ExhaustWork, AcknowledgeStart, CompleteWork, FailWork, AcknowledgeCancellation, and
AbandonDispatch directly call the verified production mutation kernels. The emitted event fields
are taken from the same command payloads. The public worker phase routes and the final worker-loss
update call the verified worker mutation. Work/worker insertion preservation is proved as a
mutation fact, while its complete public admission caller closure remains open as the report says.

Internal command-wrapper mismatch branches return ordinary errors, but the outer exhaustive match
routes each wrapper only for its exact variant. Likewise, the new `WorkDisappeared` and
`DispatchDisappeared` outcomes describe failed post-lookup mutations; no interfering mutation
occurs between the successful lookup and the target update in the inspected single-command
paths. I found no changed reachable error priority or diagnostic payload in the claimed slice.
These observations do not substitute for the still-open exact whole-reducer Result/error theorem.

`decide` continues to clone the pre-state, apply only to the clone, refresh and validate the
successor, and emit an event only after successful application. Therefore an apply error discards
the partial successor at the actual public call boundary. The unchanged replay and event-to-command
reconstruction paths remain exhaustive for the command variants. The regression suite exercises
the new release, retry/re-reserve, rollback/error-priority, terminal-payload, and replay cases, but
full replay correspondence is correctly left open.

## Material integration caveats

### Resource/selection correction is not in this package

The scheduler316 copies of `src/resource.rs` and `src/resource/capacity.rs` are byte-identical to
the frozen244 preimage. They are not the corrected files in
`/tmp/peritus-sol-scheduler-perf-final-source-20260913T003`. Therefore this immutable package alone
does not resolve the previously reviewed dense-resource performance risk. Integration must layer
the separately reviewed performance delta over the common frozen244 preimage and qualify the
combined tree.

### Worker phase update regresses logarithmic lookup

Frozen244's mutable worker update used `binary_search_by_key` over the canonical worker sequence.
Scheduler316's `set_worker_phase` instead scans from index zero until the identity matches. The
path is used by SetWorkerAvailable, DrainWorker, RemoveWorker, and the final LoseWorker update. At
the production maximum of 4,096 retained workers this changes the update lookup from logarithmic
to linear time. No runtime measurement or explicit performance acceptance was supplied. This is a
shipping caveat, not a proved functional error.

The runtime worker's narrowly scoped correction is expected to change only:

1. `src/state/lookup.rs`, to expose/reuse a verified binary-search worker-index helper; and
2. `src/state/mutation/worker_update.rs`, to apply the exact existing phase/frame semantics at
   the returned index.

A focused review should confirm the helper's returned-index identity guarantee, exact `None`
behavior under the canonical worker-state facts actually available to the mutation, unchanged
error/frame contracts, and absence of a new executable precondition or rejection guard.
