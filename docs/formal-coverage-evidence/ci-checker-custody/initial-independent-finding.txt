Verdict

PASS for the bounded current-PR trusted execution design, subject to a material
trusted-base evolution gap. BLOCKED for any durable exclusive merge-authority
claim until authority-checker transition custody is added and the documented
external App/ruleset deployment is completed.

Confirmed behavior

- The pull_request_target workflow is byte-locked by the base-compiled checker.
  It uses read-only contents permission, immutable action pins, exact event base
  and head SHA checkouts, exact checkout HEAD checks, EVENT_SHA/base equality,
  and base-is-ancestor-of-head.
- Before candidate Cargo metadata, the shell inventories the exact candidate Git
  tree with NUL-delimited records, admits only regular blobs, rejects legacy
  Cargo/Rust selectors, and requires the root Cargo config, attributes, and Rust
  toolchain file to have no base/head diff.
- The workflow builds xtask from the authority checkout into RUNNER_TEMP. Both
  `all` and `verify-trust` execute that binary from the candidate directory with
  an offline fresh Cargo home and a PATH rebuilt from resolved runner Cargo/Git
  directories plus /usr/bin:/bin. No candidate action or repository script is
  selected by the workflow.
- `all` reaches the exact authority validator through cli::execute_all ->
  reproducibility::check -> workflow_policy::validate_document ->
  workflow_authority::validate. The authority validator compares full bytes to
  its include_str base copy and separately requires exact YAML keys, values,
  order-sensitive steps, scripts, environments, and action pins.
- Reachable child processes are Cargo metadata from the base checker and Git
  inspection in protected proof-impact checks. Cargo metadata parses candidate
  manifests/dependency metadata and does not compile candidate packages, build
  scripts, or procedural macros. Git reads candidate objects/history. Candidate
  data is therefore processed; “nonexecution” is limited to no intentional
  execution of candidate code, actions, scripts, build scripts, or macros.
- Exact scripts use `set -euo pipefail`, have no continue-on-error, and the
  command chain returns nonzero on identity, tree, metadata, `all`, or
  `verify-trust` failure. Offline dependency misses fail closed.
- Retained checkpoint logs show all five focused authority mutation tests pass
  and `xtask reproducibility-check` pass. Exact workflow-byte comparison makes
  every workflow mutation fail even beyond the sampled structural mutations.

Material finding: authority checker has no transition custody

`xtask` is architecture verification class C. Protected proof-impact inventory
tracks V/H/T compilation sources and shared inputs, not ordinary xtask source.
The base checker validates candidate repository data but does not require
candidate `xtask/Cargo.toml`, `xtask/src/**`, or `xtask/tests/**` to equal the
base, and it does not require an external exact-head admission for an xtask-only
change. The checker-binding code is reached only during a specially formed
proof-impact authorization flow; an ordinary xtask-only pull request need not
enter that flow.

Consequently, a candidate can change `workflow_authority.rs`, `workflow_policy.rs`,
`workflow_run.rs`, or another authority-critical checker input while leaving the
canonical workflow and protected formal inputs unchanged. The current run still
uses the safe base binary and passes. After that candidate is merged, the changed
checker becomes the base binary for later pull requests and can accept a weakened
workflow or policy. The focused tests mutate workflow bytes but do not exercise
this cross-revision checker-source transition.

This is a two-change trusted-computing-base poisoning path. It does not permit
candidate execution in the current run and does not worsen today's documented
candidate-controlled Gate A. It does block treating a future source-bound App
that merely republishes this job's conclusion as durable exclusive authority.
The smallest complete design correction is to inventory every input that can
change the authority checker binary and reject its base/head drift by default,
with legitimate changes admitted only by a separately controlled exact-head
bootstrap decision. This can retain zero GitHub approvals and maintainer
self-merge; the admission decision belongs to the external authority producer,
not candidate-committed records.

Claims and deployment boundary

The docs accurately label this increment “validation-ready and
enforcement-incomplete,” state that no App reporter/credential exists, preserve
zero GitHub approvals and maintainer self-merge, and require a later reporter to
publish a source-bound check on the exact head. They also correctly warn that the
first pull_request_target workflow cannot validate its own bootstrap.

The App guidance binds a trusted-checker revision but does not establish how a
new checker revision becomes trusted. Workflow/dependency bootstrap language
should explicitly include all authority-checker inputs. “Legitimate authority
update” is broader than the implemented workflow-byte custody if read to include
checker source changes.
