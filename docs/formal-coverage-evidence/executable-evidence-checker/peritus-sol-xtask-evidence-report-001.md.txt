## Code-ready behavior

The checker now parses function declarations with the existing token lexer, function-body scanner,
and pinned Verus signature grammar. It records the declaration's actual mode, lexical `verus!`
enclosure, function nesting, exact conditional-compilation envelope, and exact Cargo-test status.
It then joins declaration metadata to the existing owner-path parser by the same-name declaration
occurrence ordinal. Both token streams count every same-name function, including locals, before
owner-path filtering, so two same-name functions on one source line cannot inherit each other's
mode or configuration.

Static manifest validation now requires:

- Cargo-test evidence to resolve to one non-local, non-ignored exact `#[test]` enabled either
  unconditionally or only by conventional `#[cfg(test)]`;
- Cargo-Verus evidence to resolve to one unconditional, non-local executable, proof, or spec
  declaration lexically inside `verus!`;
- the fully qualified source module and associated-item owner to match exactly.

Any other `cfg`, `cfg_attr`, malformed configuration, ignored test, nested function, duplicate
declaration, ordinary Rust function, wrong owner, or ambiguous source path fails closed. Actual
Verus `const fn` definitions are eligible, while ordinary Rust `const fn` definitions remain
ineligible.

The strict proof-scope runner carries the parsed source mode into the fresh package verification.
Every registered executable or proof symbol must appear in Verus's selected-function inventory and
have a successful solver query in the same `exec` or `proof` mode. A registered spec symbol must be
selected; it need not have a standalone solver query. Conflicting query modes, missing selections,
failed or partial verification results, wrong toolchain identities, and sibling-root substitutions
remain errors.

Regression coverage includes comments/literals, actual executable/proof/spec modes, the prior
ordinary-`const fn` bypass, disabled and attributed configuration, nested and duplicate declarations,
wrong owners, ignored Cargo tests, and same-name same-line declarations in different owners and
modes. The same-line regression specifically keeps `Model::checked` as `spec` and
`Runtime::checked` as `exec`, then verifies that the executable still requires an `exec` compiler
query.

## Trust boundary and remaining deployment work

The static manifest pass establishes source eligibility and exact ownership; it does not establish
that Verus verified the symbol. `formal-inventory` is explicitly audit-only and does not assert
freshness of any retained compiler-scope observation. The fresh strict CI proof-scope run is the
compiler-backed gate that requires selection and same-mode successful queries.

A selected symbol or successful query does not itself prove production correspondence, discharge an
obligation, authenticate the runner, or authorize a review. Those remain the responsibility of the
actual proof contracts, production-caller mapping, trusted workflow execution, and independent review
records. This source is code-ready for hash-guarded integration and final shared-tree qualification;
deployment and external required-status authority remain separate prerequisites.
