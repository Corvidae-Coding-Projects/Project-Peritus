# Release contract assets

This directory contains the stable schemas and incomplete operator templates used to assemble H4
release evidence. These source files describe what evidence must look like; they are not evidence
that a release candidate was built, signed, audited, or approved.

- `schemas/` defines the stable JSON interchange boundaries, including the exact H4 qualification
  plan accepted by `peritus-h4 finalize`.
- `templates/` provides a complete-shaped but deliberately `not-satisfied` H4 plan and supporting
  document examples. Replacing a sentinel is necessary but never sufficient evidence.
- `assets/` documents the externally generated artifact layout.

Canonical machine documents are compact JSON generated by the H4 crates. Pretty-printing is a
display operation and must not be substituted for the bytes whose digest or signature is recorded.

Actual evidence belongs in a candidate-specific external evidence root. H4 admits it only after
checking its digest, exact candidate binding, and detached signature. The release decision remains
fail-closed when any required native-host, soak, migration, recovery, reproducibility, or
independent-review record is missing.

The operator template lists all 25 signed inputs, 11 fresh-subject campaigns, two build witnesses,
25 acceptance criteria, and the independent final audit. The campaign object for each fresh subject
must be retained and signed as the payload for that campaign kind; unsigned cleanup values in the
plan cannot change the observation.

See the [release policy](../docs/h4-release-policy.md),
[qualification guide](../docs/h4-release-qualification.md), and
[migration and recovery runbook](../docs/release-migration-recovery.md) for the full workflow.
